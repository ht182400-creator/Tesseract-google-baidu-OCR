# 03 — SW 路线构建 Tesseract（Windows / MSVC）编译问题与解决方案汇总

> 环境：Windows 10/11（中文系统，默认代码页 936 / GBK）、VS2022（MSVC 14.3x）、SW 客户端 v1.0.0
> 构建命令：`sw -platform Win64 -config r build -Dwith-tests=1`（通过 `D:\tools\sw_build.bat` 启动）
> 构建目标总数：**4475**（依赖 + Tesseract 自身源码 + 测试），构建已于 **4475/4475** 全部完成。
>
> 本文档汇总构建全过程遇到的所有编译/脚本错误，按"现象 → 根因 → 解决方案"组织，便于复现与后续排查。

---

## 0. 背景：为什么用 SW + 为什么要 VS2022

- Tesseract 官方推荐用 CMake + vcpkg，但本项目尝试走 **SW（Software Network）依赖管理**路线。
- **关键前提**：SW 的 driver（cppan2/client2）依赖使用了 C++23 特性（如 `std::basic_string::contains`）。
  - VS2019 的 MSVC 14.29 **不支持 C++23** → driver 自身编译失败（`error C2039: "contains" 不是 std::basic_string 的成员`），SW 路线在 VS2019 上**不可行**。
  - 必须安装 **VS2022**（MSVC 14.3x）才能编过 driver。VS2022 与 VS2019 可 side-by-side 共存，不互相覆盖。
- 中文 Windows 默认 ANSI 代码页 936（GBK），而 Tesseract 及大量依赖（expat / fontconfig / glib / cairo / pango 等）源码是 **UTF-8**，由此衍生出本文大部分编码类问题。

## 1. `sw_build.bat` 中文 REM 被 cmd 误读为命令

| 项 | 内容 |
|---|---|
| 现象 | 运行 `sw_build.bat` 报 `系统找不到指定的路径`、`'...REM' 不是内部或外部命令，也不是可运行的程序` |
| 根因 | bat 中的中文 `REM` 注释是 **UTF-8 无 BOM**，cmd 在 936 代码页下把中文行当成命令执行，`REM` 变成乱码开头的指令而非注释 |
| 解决方案 | 把 bat 里的中文 `REM` 全部改为**纯 ASCII 英文注释**；bat 文件保持纯 ASCII 无 BOM |
| 影响范围 | 仅脚本本身，不影响源码 |

**通用经验**：Windows 下的 `.bat` / `.cmd` / `.ps1` 脚本**一律用 ASCII 注释**，不要写中文 REM；要写中文说明就放进单独的 `.md` 文档。

## 2. 中文代码页（936）导致 UTF-8 源文件编译失败（C4819 / C1020）

| 项 | 内容 |
|---|---|
| 现象 | 依赖阶段 `[97/4475]` 首次失败：`expat-2.8.1/lib/random_rand_s.c` 报 `warning C4819` + `fatal error C1020: 意外的 #endif` |
| 根因 | 中文 Windows 默认 ANSI 代码页 936（GBK）。该 expat 源文件含非 ASCII 字符（版权弯引号等），MSVC 在 936 下把 UTF-8 多字节序列误读，吞掉某条 `#if` 指令，导致 `#endif` 不匹配（C1020）。**源码语法本身完全正确** |
| 解决方案 | 在 `sw_build.bat` 调用 sw 前加 `set CL=/utf-8`（cl.exe 会自动读取 `CL` 环境变量作为额外命令行参数），让编译器以 UTF-8 解析所有源文件。**无需改系统区域、无需重启、无需改源文件** |
| 影响范围 | 所有含非 ASCII 字符的源文件（依赖阶段首炸点） |

> `CL=/utf-8` 是解决中文系统下 SW / CMake / MSVC 编译 UTF-8 源文件编码错误的**通用手法**。

## 3. Tesseract 源码 `src/ccstruct/image.h` 缺 `#include <cstdint>`

| 项 | 内容 |
|---|---|
| 现象 | 进入 Tesseract 自身代码（`[2039/4475]`）报：`error C2061: 语法错误: 标识符"uint32_t"`、`error C4430: 缺少类型说明符`、`data/n/b 未声明` 等一串级联错误 |
| 根因 | `image.h` 直接 `#include <allheaders.h>`（leptonica）+ `<tesseract/export.h>` 并使用 `uint32_t`。GCC 下 leptonica 的 `allheaders.h` 间接把 `stdint.h` 拉进全局命名空间；但 **SW 的 MSVC 版 leptonica 不暴露 `uint32_t` 到全局**，于是 `uint32_t` 未声明，级联出后续所有错误 |
| 解决方案 | 在 `<allheaders.h>` 之后补 `#include <cstdint>`（让头文件自给自足） |
| 影响范围 | 仅 `image.h`。全仓库仅此文件直接 include leptonica 的 `allheaders.h`，其余 97 个使用定宽类型的头靠 Tesseract 公共头（如 `tesstypes.h`）间接带出，无此问题 |

> **切勿**用 `set CL=/utf-8 /FIstdint.h` 做全局强制包含来"一次性覆盖"——见问题 4。

## 4. `CL` 里加 `/FIstdint.h` 破坏 SW 启动探测（踩坑记录）

| 项 | 内容 |
|---|---|
| 现象 | 在 bat 里用 `set CL=/utf-8 /FIstdint.h` 后，SW 启动即 abort：`Exception ... detectMsvcPrefix: Cannot match VS include prefix (regex_search failed)` |
| 根因 | SW 启动时会先用 `cl` 跑一个**探测编译**来识别 MSVC 的 include 前缀；`/FI`（强制包含）改变了探测输出，导致 SW 的正则匹配失败、整个构建直接中断 |
| 解决方案 | **移除 `/FIstdint.h`**，仅保留 `CL=/utf-8`。`uint32_t` 问题改用问题 3 的"直接补 `#include <cstdint>`"精准修复 |
| 结论 | SW 下 **`CL` 里不能加 `/FI`**（`/utf-8` 不影响探测，可用） |

## 5. Tesseract 源码 `src/svpaint.cpp:108` `atoi(std::string)` 类型不匹配

| 项 | 内容 |
|---|---|
| 现象 | `svpaint.cpp(108): error C2664: "int atoi(const char *)": 无法将参数 1 从 "const std::string" 转换` |
| 根因 | `sv_event->parameter` 是 `std::string`，MSVC **不隐式转换**为 `const char*`（GCC 下可能因宽松或该文件通常被条件排除而未暴露） |
| 解决方案 | 改为 `atoi(sv_event->parameter.c_str())` |
| 影响范围 | `svpaint` 是调试绘图工具，非测试必需，但 `sw build` 会编译它，出错则整体退出 |

## 6. fontconfig 的 Python 生成脚本 `fc-const.py` GBK 解码失败（UnicodeDecodeError）

| 项 | 内容 |
|---|---|
| 现象 | 依赖阶段 `[3709/4475]` fontconfig `generate` 步骤失败：`fc-const.py, line 29 ... UnicodeDecodeError: 'gbk' codec can't decode byte 0xbf` |
| 根因 | SW 调起的 Python 进程**默认使用本机首选编码 GBK (cp936)**。`fc-const.py` 用 `open()` 读 fontconfig 的 `fcobjs.h`，而该文件开头带 **UTF-8 BOM（EF BB BF 的第三字节 0xBF 在 GBK 下非法）**，未指定 encoding 导致崩溃 |
| 解决方案 | 在 `sw_build.bat` 中加 `set PYTHONUTF8=1`，让所有 Python 进程默认按 UTF-8 读写（Python 3.7+ 支持） |
| 影响范围 | 所有 SW 调起的 Python 生成脚本（不止 fontconfig） |

## 7. `PYTHONUTF8=1` 后 fcconst.h 生成内容仍错（C2078 初始值设定项太多）

| 项 | 内容 |
|---|---|
| 现象 | `fcconst.h(699): error C2078: 初始值设定项太多`、`fcconst.h(531)` 同样错误 |
| 根因 | `fc-const.py` 用 `open(bfile)` **未指定 encoding**，UTF-8 BOM 没被剥离、变成 `U+FEFF` 字符混进对象名，生成脏条目 `/* FC_<BOM> */`，使数组元素数超过 `FC_MAX_BASE_OBJECT+1` |
| 解决方案 | 把 `fc-const.py` 的两个 `open()` 改为 `encoding='utf-8-sig'`（自动剥离 BOM）；并**删除已生成的坏 `fcconst.h`**，强制 SW 用修好的脚本重新生成 |
| 改动文件 | `C:\Users\ht182\.sw\storage\pkg\6c\1d\df21\src\sdir\fc-const\fc-const.py`（SW 缓存，非 git 源码） |

## 8. cairo `cairo-ft-font.c` 行内 BOM 致 C2014

| 项 | 内容 |
|---|---|
| 现象 | `[3922/4475]` cairo 编译失败：`cairo-ft-font.c(2): error C2014: 预处理器命令必须作为第一个非空白空间启动`，并连锁炸 `stddef.h` / `corecrt_search.h` 一堆"重定义/不在形参表" |
| 根因 | `cairo-ft-font.c` 第 2 行开头有一个 **UTF-8 BOM 字符（U+FEFF）** 紧跟在 `#include` 前面：`﻿#include <wchar.h>`。MSVC 把 BOM 当普通字符，导致 `#` 不再是行首第一个非空白 → C2014；后续 `#include` 解析错乱产生连锁错误 |
| 解决方案 | 用 .NET `File.WriteAllText` 剔除该文件**全部 `U+FEFF` 字符**（注意：PowerShell 的 `.Replace` 若用 `[char]` 重载不能传空字符串，需用字符串重载 `$c.Replace($bomStr, "")`，且 `.Replace(char, '')` 会报错；也不要用 `Set-Content` 以免又加回 BOM） |
| 影响范围 | cairo 包源文件（此文件由其"兄弟" cairo-rtree.c 之后紧跟编译） |

## 10. 关键反思：曾误用"给源文件加 BOM"思路（已放弃）

- 早期排查编码问题时，曾尝试用 `fix_utf8_bom.ps1` 往 `.sw` 缓存源文件**塞 UTF-8 BOM**。这是**错误方向**：
  - 编译器的 UTF-8 问题已由 `CL=/utf-8` 解决，**根本不需要给源文件加 BOM**；
  - 给文件加 BOM 反而让 Python 生成脚本（`fc-const.py` 等）读入 BOM 字符，制造出本文问题 7、8、9 这类"行内 BOM 破坏预处理 / BOM 混入标识符"的新坑。
- **最终统一方案（三件套）**：
  1. **编译**：`CL=/utf-8` —— 解决 MSVC 解析 UTF-8 源文件（含非 ASCII 字符）的编码错误；
  2. **Python**：`PYTHONUTF8=1` —— 解决 SW 调起的 Python 生成脚本默认 GBK 解码失败；
  3. **脚本内**：必要时 `encoding='utf-8-sig'` —— 解决 BOM 混入生成内容（如 fontconfig）；
  4. **已损坏缓存文件**：用 .NET `WriteAllText` 剔除行内 `U+FEFF`，绝不再用加 BOM 思路。

## 11. `sw_build.bat` 最终关键配置（已验证）

```bat
@echo off
REM Call VS2022 vcvars64 (NOT VS2019 — SW driver needs C++23 / MSVC 14.3x)
call "C:\Program Files\Microsoft Visual Studio\2022\Community\VC\Auxiliary\Build\vcvars64.bat"

REM Chinese Windows uses ANSI codepage 936 (GBK). MSVC (cl.exe) reads source files
REM in that codepage by default, so UTF-8 sources with non-ASCII chars cause C4819/C1020.
REM Inject /utf-8 via the CL env var so cl.exe parses all sources as UTF-8.
REM NOTE: do NOT add /FIstdint.h here — SW runs a cl "detect" probe at startup to find the
REM VS include prefix; /FI changes that probe's output and breaks SW's regex (detectMsvcPrefix).
set CL=/utf-8

REM Chinese Windows makes Python default to GBK (cp936) for open()/text IO. SW's dependency
REM generate scripts (e.g. fontconfig fc-const.py) open files without specifying encoding and
REM crash with UnicodeDecodeError on non-GBK bytes. PYTHONUTF8=1 forces UTF-8 as Python's
REM default text encoding for all spawned python processes.
set PYTHONUTF8=1

sw -platform Win64 -config r build -Dwith-tests=1
```

- **核心修正**：此前曾误判 `lang_model`/`recodebeam`/`unicharcompress` 为"数据缺失"。实际**数据（langdata_lstm、各语言 unicharset）都已存在**，根因是 `tessdata_unittest` 本身是一个 **git 仓库**，在 Windows 下用默认 `core.autocrlf=true` 克隆时，所有**文本文件被自动转成 CRLF**。其中 `langdata_lstm/radical-stroke.txt` 被 `src/ccutil/unicharcompress.cpp:DecodeRadicalLine` 按空格切分后，末字段带 `\r`，`strtol("3\r",...)` 解析失败 → 打印 `Invalid format in radical table at line 0: 19886 3 23 6 3` → 整个部首表解析失败 → 编码无法生成。
- **baseapi 细节**：`baseapi_test.cc:81` 读取 `phototest.gold.txt` 作 truth（CRLF），与 Tesseract 的 LF 输出逐行 diff 失败；文字本身正确。
- `lang_model` 日志里的 `Failed to read data from .../eng.config`（及 extended/extendedhin）是**无害的可选配置警告**（测试打印 "Config file is optional, continuing..."），不是失败原因。

### 15.5 修复措施（已全部实施）

1. **`baseapi`**：将 `test/testing/phototest.gold.txt` 改写为 LF（直接去除 `\r`）；并在 `test` 子模块内新增 `.gitattributes`（`/testing/phototest.gold.txt eol=lf`），使该文件以后持久以 LF 检出，避免 `git autocrlf` 再次污染。
   > 注意：`test` 是 git 子模块，不能用父仓库的 `git checkout` 操作其中的文件，必须在子模块内处理。
2. **`lang_model` / `recodebeam` / `unicharcompress`**：遍历 `tessdata_unittest/langdata_lstm` 下所有文本文件，剔除行尾 `\r`（CRLF→LF；含 NUL 字节的二进制文件跳过以免破坏）。关键修复对象是 `radical-stroke.txt`，其余 wordlist/punc/numbers 等一并修正以防后续解析隐患。
   > 注：此前曾用官方 `tesseract-ocr/langdata_lstm` 覆盖 egorpugin 的残缺版（缺 `eng.wordlist` 等），但真正让测试通过的不是"换数据"而是"去 CRLF"。若重新克隆 `tessdata_unittest`，务必以 `core.autocrlf=false` 克隆，或从官方仓库拉取后整体去除 CRLF。
